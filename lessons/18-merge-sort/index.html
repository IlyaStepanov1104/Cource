Проблема

почему O(n²) недостаточно

Почему O(n²) медленно?

  • 1 000 элементов -> ~500 000 операций OK
  • 100 000 элементов -> ~5 000 000 000 долго
  • 1 000 000 элементов -> ~500 000 000 000 очень долго
Пузырьковая сортировка 1 миллиона чисел - около 8 минут на современном ПК

Нужен другой подход

  • O(n²): каждый элемент сравниваем со всеми остальными
  • Что если разбить список на маленькие части?
  • Решить каждую отдельно и объединить результаты
Так работают "умные" сортировки с O(n log n)

Разделяй и властвуй

Divide & Conquer

Принцип Divide & Conquer

Разбиваем сложную задачу на подзадачи того же типа, но меньшего размера

Рекурсия - задача вызывает саму себя на меньших данных

Три шага D&C

1
Divide - разделить задачу на 2 меньших подзадачи
2
Conquer - решить каждую рекурсивно (до базового случая)
3
Combine - объединить результаты в ответ
Бинарный поиск - тоже D&C: каждый шаг отбрасываем половину

Merge Sort

сортировка слиянием

Идея

  • Делим массив пополам
  • Рекурсивно сортируем каждую половину
  • Сливаем два отсортированных массива в один
Базовый случай: массив из 1 элемента - он уже отсортирован

Разбиение (сверху вниз)

    [8, 3, 5, 1]       делим пополам
       /      \
   [8, 3]  [5, 1]      делим ещё
    /  \    /  \
  [8]  [3] [5] [1]     1 элемент = уже готов

Слияние (снизу вверх)

  [8]  [3] [5]  [1]    начинаем слияние
    \  /     \  /
  [3, 8]   [1, 5]      сливаем пары
      \       /
    [1, 3, 5, 8]       готово!

Как работает слияние?

  • Берём два отсортированных массива
  • Сравниваем первые элементы обоих
  • Меньший переносим в результат, двигаем указатель
  • Когда один массив кончился - добавляем остаток другого

Пример: [3, 8] + [1, 5]

Left Right Сравниваем Result
[3, 8][1, 5]3 vs 1 - берём 1[1]
[3, 8][5]3 vs 5 - берём 3[1, 3]
[8][5]8 vs 5 - берём 5[1, 3, 5]
[8]-добавляем остаток[1, 3, 5, 8]

Дерево рекурсии

Уровень 0: [8, 3, 5, 1, 9, 2, 7, 4]    <- n операций слияния
                  /           \
Уровень 1: [8,3,5,1]      [9,2,7,4]     <- n суммарно
              /   \          /   \
Уровень 2: [8,3] [5,1]  [9,2] [7,4]     <- n суммарно
            / \   / \    / \   / \
Уровень 3: [8][3][5][1][9][2][7][4]     <- базовый случай
  • Высота дерева = log n уровней
  • На каждом уровне суммарно = n операций слияния
  • Итого: O(n log n)

Почему высота = log n?

На каждом уровне массив делится пополам - размер уменьшается в 2 раза

уровень 0:  n
уровень 1:  n / 2
уровень 2:  n / 4
уровень k:  n / 2^k

Останавливаемся, когда размер = 1:

n / 2^k = 1  ->  2^k = n  ->  k = log2(n)
log2(n) - это сколько раз нужно разделить n на 2, чтобы дойти до 1

O(n log n) vs O(n²)

n O(n²) O(n log n)
1 0001 000 000~10 000
100 00010 000 000 000~1 700 000
1 000 0001012~20 000 000
Разница в 50 000 раз на миллионе элементов

Quick Sort

быстрая сортировка

Идея Quick Sort

  • Выбираем pivot - опорный элемент
  • Делим: элементы < pivot / == pivot / > pivot
  • Рекурсивно сортируем левую и правую части
  • Объединяем: left + middle + right
В отличие от Merge Sort - pivot уже стоит на своём месте, не нужно отдельно сливать

Partition: разбиение

  • Все элементы < pivot - в левую часть
  • Все элементы == pivot - в среднюю
  • Все элементы > pivot - в правую
После partition pivot стоит ровно там, где он будет в отсортированном массиве

Пример partition

Массив: [3, 6, 8, 10, 1, 2, 1], pivot = 3

left (< 3)

[1, 2, 1]

middle (== 3)

[3]

right (> 3)

[6, 8, 10]

Дальше: quick_sort([1, 2, 1]) + [3] + quick_sort([6, 8, 10])

Сложность: O(n log n) в среднем

  • Удачный pivot делит массив примерно пополам
  • Глубина рекурсии: log n уровней
  • На каждом уровне суммарно: n операций
  • Итого: O(n log n)

Худший случай: O(n²)

  • Если pivot всегда минимальный или максимальный элемент
  • Пример: [1, 2, 3, 4, 5], pivot = первый элемент
  • left=[], middle=[1], right=[2,3,4,5] - дерево превращается в цепочку
  • Глубина n вместо log n -> O(n²)
Решение: не брать первый или последний - брать средний или случайный

Случайный pivot

  • Вероятность n раз подряд выбрать плохой pivot: (2/n)^n - практически ноль
  • Ожидаемое время: O(n log n) при любых входных данных
  • Именно этот подход используют реальные реализации Python, C++, Java

Merge Sort vs Quick Sort

Сравнение

Merge Sort Quick Sort
Лучший случай O(n log n) O(n log n)
Средний случай O(n log n) O(n log n)
Худший случай O(n log n) O(n²)
Доп. память O(n) - нужен буфер O(log n)
Стабильность стабильная нестабильная
Скорость на практике хорошая обычно быстрее

Почему Quick Sort быстрее на практике?

Оба алгоритма - O(n log n). Но за этим скрывается константа:

  • Merge Sort на каждом уровне создаёт новые массивы - дорогое выделение памяти
  • Quick Sort переставляет элементы прямо в исходном массиве - без аллокаций
  • Работа с одним массивом = данные в кеше процессора = быстро
Асимптотика говорит "одинаково", но константа - это реальные секунды

Когда что выбирать?

Merge Sort

  • Нужна гарантия O(n log n)
  • Нужна стабильность
  • Сортировка связных списков
  • Внешняя сортировка (файлы)

Quick Sort

  • Нужна максимальная скорость
  • Данные помещаются в память
  • Ограниченная память
  • Случайные входные данные
sorted() в Python использует Timsort - гибрид Merge Sort + Insertion Sort

Что запомнить

  • D&C: разделить - решить рекурсивно - объединить
  • Merge Sort: делим пополам и сливаем - O(n log n) всегда
  • Quick Sort: pivot разбивает массив - O(n log n) в среднем, случайный pivot убирает O(n²)
  • O(n log n) быстрее O(n²) в тысячи раз на больших данных
