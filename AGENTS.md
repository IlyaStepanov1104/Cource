# AGENTS.md

This file provides guidance to Codex (claude.ai/code) when working with code in this repository.

## Что это

Статический сайт курса индивидуальных занятий по программированию. Главная страница (`index.html`) подгружает `lessons.json` и рендерит карточки занятий с презентациями и домашними заданиями. Презентации строятся на [Reveal.js](utils/js/reveal.js).

## Команды

```bash
npm install   # один раз
npm run dev   # dev-сервер на http://localhost:8001
```

Сборки нет — сайт полностью статический, Vite используется только как dev-сервер.

## Потоки (табы)

На сайте два независимых потока, переключаются табами на главной и в админке (`?track=ege`):

| Поток | Данные | Презентации | Практика | Расписание |
|---|---|---|---|---|
| Программирование | `lessons.json` | `lessons/<NN-slug>/` | `practice/<NN-slug>/` | вс 11:00 (60) / пн 18:00 (90) |
| ЕГЭ | `ege.json` | `lessons-ege/<NN-slug>/` | `practice-ege/<NN-slug>/` | вт 19:00 (60) |

Нумерация занятий в каждом потоке своя. Правила генерации презентаций и практики для ЕГЭ те же, что для программирования. Список потоков задан константой `TRACKS` в `index.html` и `admin/index.html`, файлы для сохранения - `TRACK_FILES` в `vite.config.js`.

## Оплата

Общий счётчик по обоим потокам ведёт админка. Оплаты лежат в `payments.json` (`{ "payments": [{ "date", "lessons", "note" }] }`, файл в `.gitignore` - только локально), добавляются кнопкой «+ Оплата». Занятия обоих потоков с даты первой оплаты идут по порядку дат и по очереди списывают оплаченные уроки; в шапке - сколько осталось, на карточке - сколько останется к этому занятию (2 и меньше - пора платить).

## Формат занятий

- Программирование: преподаватель объясняет материал и пишет код в формате лайвкодинга; ученик самостоятельно практикуется в домашнем задании. Блоки с кодом на слайдах оформлять как совместный разбор или лайвкодинг, без указаний ученику писать код самостоятельно на время.
- ЕГЭ: на занятиях есть самостоятельная практика, где код пишет ученик.
- В презентациях не размещать реализации алгоритмов и готовые решения задач. Допустимы только небольшие отрывки кода для разбора ДЗ или иллюстрации новых методов и функций. Для лайвкодинга на слайдах оставлять условия, примеры входных данных и ответов, схемы и формулы; реализации хранить в материалах преподавателя.

## Архитектура

- **`lessons.json`** / **`ege.json`** — источники данных потоков. Занятие скрыто до наступления `date` (добавь `?view_all=true` в URL для предпросмотра).
- **`index.html`** — вся логика главной страницы встроена в `<script>`: fetch → renderLessons → DOM-генерация карточек.
- **`lessons/<NN-slug>/presentations/<N-slug>/index.html`** — каждая презентация самодостаточна, использует Reveal.js из `/utils/`.
- **`utils/`** — общий Reveal.js, шрифты, стили. Пути абсолютные (`/utils/...`), поэтому обязательно нужен dev-сервер.

- На видимых слайдах не указывать номер занятия и длительность (например, «Занятие 41 · 60 минут»).

## Структура презентации

### Качество объяснения и порядок работы

Эти правила уточняют навыки `gen-presentation` и `skeleton-presentation` для этого проекта. Цель — готовая к проведению урока презентация с первой просьбы; пользователь не должен дописывать объяснения за генератором.

- Перед подготовкой восстановить договорённости из текущего диалога и материалов курса, прочитать прошлое ДЗ и содержательные фрагменты двух соседних презентаций. Использовать их для понимания уровня и языка курса; не копировать устаревшие нарушения правил (например, готовые реализации на слайдах).
- Сначала спроектировать ход объяснения, затем HTML. Для новой идеи обычно нужны: понятная задача и данные → конкретный выбор → его последствия → объяснение причины → общее правило. Это ориентир рассуждения, а не обязательные пять слайдов для каждой темы.
- Показывать объекты задачи раньше абстрактных обозначений. Например, сначала занятия с временем начала и конца, затем интервалы; сначала сравнить два выбора, затем назвать локальную и общую цель. Новые термины объяснять при первом употреблении.
- Писать естественным русским языком полными, связанными мыслями. Избегать фраз вроде «ранний конец безопасен», «доверять шагу», «динамика учитывает альтернативы, которые жадность теряет». Называть конкретное действие и то, почему оно помогает.
- Сохранять один пример и его обозначения при переходе от условия к разбору и лайвкодингу. Новый пример вводить ради нового свойства и объяснять переход. Не менять данные только ради разнообразия.
- Вопрос на слайде должен иметь достаточно исходных данных для ответа и последующее объяснение на видимых слайдах. Ключевой контрпример, причина выбора и причинно-следственная связь должны быть видны на слайдах. Не добавлять `aside.notes` и скрытые методические заметки в HTML: преподаватель ими не пользуется. Подсказки, ответы и дополнительные детали хранить только в отдельном плане в репозитории решений.
- Сохранять оформление предыдущих презентаций того же потока: настройки Reveal, масштаб заголовков и текста, титульный слайд, цвета и общие компоненты. Не создавать собственную тему и не переопределять глобальную типографику без запроса пользователя. Кастомные стили — только для специфических схем. При визуальной проверке сравнить новую презентацию с предыдущими при одинаковом размере окна.
- Различать трассировку, доказательство и контрпример. Проверять, что пример действительно показывает заявленное свойство. Заголовок «Почему стратегия ошибается?» требует случая, где её ответ хуже другого допустимого ответа; несколько успешных тестов не доказывают оптимальность.
- Подбирать наглядность по задаче: интервалы на общей временной оси, изменения массива по шагам, покрытие через отмеченные элементы. Таблица или набор карточек не заменяют схему, если ученику приходится мысленно восстанавливать отношения между объектами.
- Математическая корректность обязательна, но не добавлять необъяснённые термины и оговорки ради демонстрации строгости. Существенные условия сформулировать понятно; дополнительные тонкости вынести в отдельные материалы преподавателя, не делая видимое утверждение ложным.
- Планировать время на объяснение, ответы и лайвкодинг, а не по количеству кликов. Фрагменты раскрывают шаги мысли; не скрывать нужное условие и не дробить каждую подпись ради нормы кликов. Не сжимать рассуждение до четырёх пунктов ради шаблона.
- Скелет сохраняет согласованные темы и порядок, но допускает разделение перегруженного слайда и объединение повторов. Точное количество слайдов обязательно только по прямому требованию пользователя. При просьбе о полной презентации самостоятельно пройти планирование, генерацию и проверку без промежуточного согласования скелета; при просьбе только о скелете выдать скелет.
- До сдачи перечитать отдельно весь видимый текст по порядку, без заметок: понятны ли данные, откуда следует каждый вывод, отвечает ли содержание заголовку, нет ли скачков и повторов. Исправить найденные проблемы, а не передавать их пользователю списком замечаний.
- Проверить числовые примеры, соответствие условиям, ссылки и согласованность с практикой. Затем просмотреть презентацию в браузере, включая промежуточные раскрытия фрагментов: читаемость, переполнение, схемы и переходы. Проверка HTML или числа слайдов не заменяет содержательную и визуальную проверку. Если визуальная проверка недоступна, явно сообщить об этом.
- В ответе сообщать готовый результат и существенные ограничения проверки. Количество слайдов, фрагментов и отсутствие ошибок HTML не являются доказательством качества урока.

Шаблон — `lessons/01-intro/presentations/1-intro/index.html`.

Каждая презентация подключает:
1. `/utils/css/reveal.css` + тему
2. `/utils/css/custom-base.css` — общие компоненты (`.opinion`, `.compare`, `.tools-list`, `.timeline`, `.arch-flow`)
3. `css-custom/custom.css` — стили, уникальные для данной лекции

Кастомный веб-компонент `<code-example>` рендерит живой HTML+CSS preview прямо на слайде.

## Добавление занятия

1. Добавить запись в `lessons.json`.
2. Создать `lessons/<NN-slug>/presentations/<N-slug>/`, скопировав из `01-intro/presentations/1-intro/`.
3. Обновить `presentations` в `lessons.json` с правильным `link`.
